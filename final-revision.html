Lec 1

أساسيات هندسة البرمجيات What is Software & SE · Attributes · Crises · Application Types — Sommerville Ch.1

التعريفات الأساسية

  • Software = Programs + Data + Documentation — السوفتوير مش بس الكود! برامج + بيانات + توثيق. والتوثيق نوعين: System documentation (للمطورين) وUser documentation (للمستخدم). ✏️ ليها رسمة
  • Software Engineering = an engineering discipline concerned with ALL aspects of software production — تخصص هندسي بيهتم بكل جوانب إنتاج السوفتوير من الفكرة للصيانة.
  • أنشطة الـ SE الأربعة: Specification → Development → Validation → Evolution (احفظها S-D-V-E).
  • SE vs Computer Science: الـ CS = نظريات وأساسيات. الـ SE = التطبيق العملي لبناء وتسليم سوفتوير مفيد.
  • SE vs System Engineering: هندسة النظم بتشمل النظام كله (hardware + software + process)، والـ SE جزء منها.
  • التكاليف: ≈ 60% development + 40% testing، وفي الأنظمة المخصصة تكلفة الـ evolution بتعدي تكلفة التطوير.

صفات السوفتوير الجيد — Attributes of Good Software

  • Maintainability — قابل للتعديل والتطوير مع تغير احتياجات العميل.
  • Dependability & Security — موثوق وآمن: ميسببش ضرر لو فشل، ومحمي من المستخدمين الخبيثين.
  • Efficiency — مايهدرش موارد: سرعة استجابة، معالجة، ذاكرة.
  • Acceptability — مقبول للمستخدمين: مفهوم وقابل للاستخدام ومتوافق مع أنظمتهم.
احفظهم بكلمة MADE: Maintainable · Acceptable · Dependable · Efficient

مثلث التصميم + أزمات السوفتوير

  • الـ 3 اهتمامات الأساسية في التصميم: Time · Cost · Quality — مثلث: حسّن اتنين، التالت هيتأثر. ✏️ ليها رسمة
  • Software Crisis = مشاريع Late, Over budget, Unreliable, Hard to maintain, Performed poorly.

Scotland flights 2009 ✈️عطل في نظام مراقبة جوية → تأخير رحلات، رجعوا للـ backup، اتصلح في ساعات

أنواع التطبيقات الـ 8 — Application Types

  • Stand-alone applications — على جهاز واحد من غير نت (photo editor).
  • Interactive transaction-based — على سيرفر بعيد والمستخدم بيوصله (e-commerce).
  • Embedded control systems — بتتحكم في أجهزة. الأكثر انتشاراً (غسالة).
  • Batch processing systems — دفعات كبيرة من البيانات (مرتبات شهرية).
  • Entertainment systems — ترفيه (ألعاب).
  • Modeling & simulation — محاكاة عمليات فيزيائية (طقس).
  • Data collection systems — تجمع بيانات بـ sensors (محطة طقس).
  • Systems of systems — أنظمة مكونة من أنظمة تانية.
مفيش "أفضل طريقة واحدة" لكل الأنظمة — ده اسمه Software Engineering Diversity. ولو سُئلت "أكتر نوع منتشر؟" → Embedded.

Lec 3

نماذج عمليات البرمجيات Process Models: Waterfall · Evolutionary · Reuse · Spiral · V-Model · RUP · Testing Stages

الأساسيات

  • Software Process = مجموعة أنشطة منظمة مطلوبة لتطوير نظام برمجي. Process Model = تمثيل مجرد للعملية من منظور معين.
  • Plan-driven = كل حاجة مخططة مسبقاً. Agile = تخطيط تدريجي. معظم المشاريع الحقيقية مزيج من الاتنين.
  • النماذج العامة الثلاثة (3 Generic Models): ① Waterfall ② Evolutionary Development ③ Reuse-oriented (Integration & Configuration).

النماذج واحد واحد

النموذجفكرته + مراحلهكلمته السحرية
🌊 Waterfall ✏️خطي تسلسلي — كل مرحلة تخلص قبل اللي بعدها: Requirements → Design → Implementation → Testing → Maintenancelinear, sequential
🧬 Evolutionaryنوعان: Exploratory (يبدأ من متطلبات مفهومة) وThrow-away prototyping (يبدأ من متطلبات غامضة والـ prototype بيترمي)interleaved activities
♻️ Reuse-orientedRequirements Spec → Component Analysis → Requirements Modification → Design with Reuse → Development & Integration → Validation. أنواع المكونات: Web services · Object collections · Stand-alone systemsexisting components
🌀 Spiral (Boehm 1988) ✏️حلقات — كل لفة 4 قطاعات: ① Objective Setting ② Risk Assessment & Reduction ③ Development & Validation (Engineering) ④ Planningrisk-driven
✅ V-Model ✏️لكل مرحلة تطوير (يسار) مرحلة اختبار مقابلة (يمين) — اكتشاف مبكر للأخطاءverification per phase

أشهر 4 فخاخ في شيت 3: ① "NOT a Waterfall phase?" → Iteration (مفيش تكرار في الشلال). ② "NOT an Agile principle?" → Comprehensive documentation. ③ "Spiral: prototypes built in which phase?" → Engineering مش Risk Analysis! ④ "NOT a V-Model characteristic?" → "linear sequential like Waterfall".

الأنشطة + الاختبار + التسليم التدريجي

  • الـ 4 Process Activities: Specification → Design & Implementation → Validation → Evolution.
  • الـ Requirements Engineering جوه الـ Specification: Feasibility Study → Elicitation & Analysis → Specification → Validation.
  • مراحل الاختبار الخمسة (بالترتيب): Unit → Module → Sub-system → System → Acceptance. الـ Sub-system تركيزه على interface testing، والـ Acceptance بـ real customer data.
  • Incremental development: تسليم على دفعات — الأولوية العالية الأول، مخاطر أقل، لكن صعب مع العقود الحكومية اللي عايزة spec كامل.
  • CASE tools = برمجيات بتدعم تطوير البرمجيات. 3 تصنيفات: Functional · Process · Integration.
صفات العملية الفعالة: Flexibility · Predictability · Adaptability — ومش منهم أبداً Rigidity (الجمود).
Lec 4

الأجايل و الـ XP Agile Manifesto · 5 Principles · Extreme Programming · TDD · Pair Programming

ليه Agile؟ + الـ Manifesto

  • ظهر في late 1990s عشان يقلل وقت التسليم جذرياً — السوق سريع التغير ومستحيل تثبت المتطلبات.
  • في Agile الأنشطة inter-leaved (متشابكة): التحديد والتصميم والتنفيذ والاختبار مع بعض، والمخرجات بتتحدد بالـ negotiation أثناء التطوير.
بنقدّر أكتر ✅على حساب ⬇️
Individuals & interactions (الناس والتواصل)Processes and tools
Working software (برنامج شغال)Comprehensive documentation ⚠️
Customer collaboration (التعاون مع العميل)Contract negotiation
Responding to change (التكيف مع التغيير)Following a plan
المبادئ الخمسة (CIPEM): Customer involvement · Incremental delivery · People not process · Embrace change · Maintain simplicity

الـ XP — Extreme Programming

  • أكتر منهج Agile تحديداً للممارسات الهندسية. نسخ جديدة عدة مرات في اليوم، تسليم للعميل كل أسبوعين، وكل الاختبارات لازم تنجح لكل build.
  • الـ 10 ممارسات: Incremental planning · Small releases · Simple design · Test-first development · Refactoring · Pair programming · Collective ownership · Continuous integration · Sustainable pace · On-site customer.
  • User stories — المتطلبات بتتكتب على كروت كقصص، والفريق بيكسرها لـ tasks للتقدير.
  • Refactoring = تحسين الكود باستمرار من غير تغيير وظيفته — الـ XP بيرفض "التصميم للتغيير المستقبلي" لأن التغيير مش متوقع بدقة.
  • Test-first / TDD = اكتب الاختبار قبل الكود — بيوضح المتطلبات، والاختبارات برامج قابلة للتشغيل التلقائي. مشاكله: المبرمجين بيفضلوا البرمجة، صعوبة اختبار الواجهات، صعوبة الحكم على الاكتمال.
  • Pair programming = اتنين على جهاز واحد — مراجعة مستمرة، معرفة مشتركة، ومش بالضرورة أقل كفاءة (فيه دليل إنه أكفأ من اتنين منفصلين).
Sustainable pace يعني: ممنوع الـ overtime الكتير لأنه بيقلل جودة الكود والإنتاجية — مش "اشتغل أكتر".
Lec 5

إدارة مشاريع الأجايل — Scrum Scrum Phases · Terminology · Sprint Cycle · Scaling · Multi-team Scrum

Scrum الأساسي

  • Scrum = منهج Agile لإدارة الـ iterative development (مش ممارسات محددة زي XP). عملية empirical: ملاحظة + تجربة.
  • 3 أعمدة: Transparency · Inspection · Adaptation.
  • 3 مراحل: Outline Planning → Sprint Cycles → Closure.
  • الأساس اللي بيربط الفريق: TRUST (الثقة).
  • 5 قيم (C-F-C-R-O): Courage · Focus · Commitment · Respect · Openness.

التوسع والمشاكل العملية

  • Scaling UP = استخدام Agile لأنظمة كبيرة. Scaling OUT = إدخال Agile في منظمة كبيرة تقليدية.
  • مشاكل Agile العملية الـ 3: ① الـ informality بتتعارض مع العقود ② مناسب للتطوير الجديد مش الـ maintenance ③ اتصمم لفرق صغيرة في مكان واحد مش distributed teams.
  • مشاكل الصيانة الـ 3: Lack of documentation · Keeping customers involved · Team continuity.
  • Brownfield = تطوير سوفتوير جديد في وجود أنظمة legacy قديمة (عكس Greenfield).
  • Multi-team Scrum — 4 آليات: Role replication · Product architects · Release alignment · Scrum of Scrums.
Lec 6

هندسة المتطلبات Requirements Engineering: Types · NFR Metrics · SRS Document · Insulin Pump Spec

مستويات وأنواع المتطلبات

  • User requirements = لغة طبيعية + رسوم بسيطة، للعميل، مستوى عالي (abstract). System requirements = وثيقة منظمة مفصلة، للمطورين، ممكن تكون جزء من عقد.
  • الأنواع الثلاثة: ① Functional — النظام يعمل إيه (خدمات ووظائف). ② Non-functional — قيود على الكيفية (سرعة، أمان، توافر). ③ Domain — قيود من مجال التشغيل (قوانين طبية/مالية).
  • تصنيف الـ NFR: Product (سلوك المنتج: متاح من 08:30–17:30، downtime ≤ 5 ثواني) · Organizational (سياسات المؤسسة: الدخول بكارت الهيئة الصحية) · External (خارجي: قانون الخصوصية HStan-03-2006). ✏️ شجرة NFR ليها رسمة
  • Complete = كل الوظائف موصوفة. Consistent = مفيش تعارض. عملياً مستحيل تحقق الاتنين 100%.
"النظام يكون سهل الاستخدام" = Goal مش requirement! الـ requirement الحقيقي لازم يكون testable برقم: "بعد 4 ساعات تدريب، أخطاء المستخدم ≤ 2 في الساعة". مقاييس مهمة: Speed → transactions/sec · Reliability → mean time to failure · Ease of use → training time · Portability → % target-dependent statements.

وثيقة الـ SRS + طرق الكتابة

  • SRS (Software Requirements Document) = البيان الرسمي للمطلوب. بتقول WHAT مش HOW — مش وثيقة تصميم!
  • مستخدميها: Customers (يتأكدوا من احتياجاتهم) · Managers (تخطيط) · System Engineers (الفهم) · Test Engineers (الاختبارات) · Maintenance Engineers (الصيانة).
  • هيكلها: Preface → Introduction → Glossary → User Requirements → System Architecture → System Requirements Spec → System Models → System Evolution → Appendices → Index.
  • 5 طرق لكتابة المتطلبات: Natural language · Structured natural language · Design description languages · Graphical notations (UML) · Mathematical specifications.
  • مشاكل اللغة الطبيعية الـ 3: Lack of clarity · Requirements confusion · Requirements amalgamation (خلط أكتر من متطلب في جملة).

مثال الـ Insulin Pump — أرقام بتيجي في الامتحان

  • المنطقة الآمنة للسكر: 3–7 وحدات. المدخلات: r0, r1, r2 (أقدم → أحدث قراءة).
  • CompDose = 0 لو السكر ثابت أو بينزل. لو بيزيد بمعدل متزايد: CompDose = round((r2−r1)/4)، ولو النتيجة صفر → MinimumDose.
  • Pre-condition: الخزان فيه على الأقل أقصى جرعة مسموحة. Post-condition: r0←r1 وr1←r2.
  • الـ Form-based spec بتقلل الغموض، والـ Tabular spec ممتازة لما يكون فيه سيناريوهات متعددة.
Lec 7

عملية هندسة المتطلبات RE Process: Elicitation · Ethnography · Validation · Change Management

الأنشطة والدورة

  • أنشطة الـ RE الأربعة: ① Elicitation ② Analysis ③ Validation ④ Management — عملية iterative متشابكة، بتترسم كـ spiral. ✏️ ليها رسمة
  • دورة الـ Elicitation الرباعية: Discovery → Classification & Organization → Prioritization & Negotiation → Specification → وترجع تاني.
  • مشاكل الـ Elicitation الخمسة: ① الناس مش عارفة عايزة إيه ② كل واحد بيتكلم بلغته ③ متطلبات متعارضة ④ عوامل سياسية وتنظيمية ⑤ المتطلبات بتتغير أثناء التحليل.
  • Stakeholders في MHC-PMS (8): Patients · Doctors · Nurses · Receptionists · IT staff · Ethics manager · Health care managers · Records staff.

تقنيات الجمع

  • Interviews: نوعان — Closed (أسئلة محددة مسبقاً) وOpen (نقاش مفتوح). كويسة للفهم العام، مش كويسة للـ domain requirements بسبب الـ tacit knowledge (المعرفة الضمنية اللي الخبير مش واعي بيها).
  • Ethnography: مراقبة الناس وهي بتشتغل فعلاً مش زي ما بتقول. بتكشف العوامل الاجتماعية والتنظيمية. عيبها: متقدرش تكتشف features جديدة — أداة فهم مش ابتكار.
  • Focused ethnography: اتطورت في مشروع air traffic control — بتدمج الـ ethnography مع الـ prototyping.

التحقق وإدارة التغيير

  • قاعدة الـ 100×: إصلاح خطأ في المتطلبات بعد التسليم بيكلف 100 ضعف إصلاح خطأ تنفيذ.
  • الفحوصات الخمسة: Validity · Consistency · Completeness · Realism · Verifiability.
  • تقنيات الـ Validation الثلاثة: Requirements reviews · Prototyping · Test-case generation.
  • فحوصات الـ Review الأربعة: Verifiability · Comprehensibility · Traceability · Adaptability.
  • عملية إدارة التغيير: Identified Problem → Problem Analysis & Change Spec → Change Analysis & Costing → Change Implementation → Revised Requirements. ✏️ ليها رسمة
  • عناصرها الأربعة: Requirements Identification (unique ID) · Change Management Process · Traceability Policies · Tool Support.
Lec 8

نمذجة الأنظمة — UML System Modeling: Perspectives · Context · Use Case · Sequence · Class · State/Activity

الأساسيات والمنظورات

  • System Modeling = تطوير نماذج مجردة للنظام، كل نموذج بيعرض منظور مختلف. الـ UML هو اللغة القياسية.
  • المنظورات الأربعة: ① External → Context model ② Interaction → Use case + Sequence ③ Structural → Class diagram ④ Behavioral → State + Activity.
  • أهم 5 أنواع UML: Activity · Use Case · Sequence · Class · State.
  • 3 استخدامات للنماذج: ① تسهيل النقاش (مسموح تكون ناقصة) ② توثيق نظام موجود (لازم accurate) ③ توليد الكود (لازم correct AND complete).

النماذج واحد واحد — كل دول ليهم رسومات ✏️

  • Context Model: بيحدد حدود النظام (system boundary) — قرار "سياسي". بيعرض الأنظمة التانية حواليه. الـ Mentcare حواليه: Patient record · Admissions · Management reporting · Prescription · HC statistics · Appointments systems.
  • Use Case Diagram: كل use case = مهمة فيها تفاعل خارجي. الـ Actors ممكن بشر أو أنظمة. الـ receptionist عنده 5: Register patient · Unregister · View info · Transfer data · Contact patient.
  • Sequence Diagram: الـ objects فوق + dotted lifelines نازلة + أسهم أفقية للرسائل. مثال: ViewInfo(PID) → report → authorize → [OK: info / FAIL: error].
  • Class Diagram: صندوق من 3 أقسام: Name | Attributes | Operations. الـ Association = خط بعلاقة وأرقام (multiplicity مثل 1..*).
  • Generalization (الوراثة): الـ subclass بيرث صفات وعمليات الـ superclass ويضيف بتاعته. هرم الدكاترة: Doctor → Hospital doctor / General practitioner → Consultant / Team doctor → Trainee / Qualified.
  • Aggregation: علاقة "جزء من" — معينة ◇ فاضية. Patient record = Patient (1) + Consultations (1..*).
  • Behavioral models: الاستجابة لمحفز Data أو Event. مثال الـ Activity: insulin pump — sensor → compute sugar → calculate insulin → control pump.
الفرق المحبوب للدكتور: الـ Context model بيعرض الأنظمة اللي حوالين النظام بس، أما الـ Process model (Activity diagram) بيعرض النظام بيُستخدم إزاي جوه العمليات. والـ Structural = صورة ساكنة، الـ Behavioral = ديناميكي.
Lec 9

التصميم والتنفيذ Architectural Design · Patterns · Reuse · Configuration Management · Open Source

التصميم المعماري

  • Architectural Design = أول مرحلة في التصميم — تحديد الـ subsystems وعلاقاتها. الحلقة بين الـ specification والتصميم التفصيلي.
  • مستويان: In the small (برنامج واحد) وIn the large (أنظمة enterprise كاملة).
  • 3 مزايا للمعمارية الصريحة: Stakeholder communication · System analysis (early) · Large-scale reuse.
  • 4 منظورات (Views): Logical (objects/classes) · Process (run-time) · Development (تقسيم الكود) · Physical (التوزيع على الأجهزة).

الأنماط المعمارية — Architectural Patterns ✏️

النمطالفكرة + مثالمزايا / عيوب
🗄️ Repositoryكل الـ subsystems بتتشارك مستودع مركزي واحد. مثال: IDE (Editor, Compiler, Debugger حوالين مستودع)+ مشاركة بيانات فعالة / − single point of failure + bottleneck
🔧 Pipe-and-Filterمراحل متسلسلة، كل filter بياخد input ويحوّله. مثال: Compiler: Lexical → Syntax → Semantic → Code generation، وكمان الـ ATM+ تبديل أي filter بسهولة / − لازم توافق صيغة البيانات
🏢 Layeredطبقات — كل طبقة بتخدم اللي فوقها. مثال: UI → UI Management → Business Logic → System Support (DB+OS)+ تعديل طبقة من غير الباقي / − أداء أبطأ أحياناً

إعادة الاستخدام + إدارة الإعدادات + المصادر المفتوحة

  • 4 مستويات Reuse: Abstraction (patterns) → Object (libraries) → Component (frameworks) → System (COTS).
  • 4 تكاليف Reuse: Search & evaluation · Purchase · Adaptation · Integration — إعادة الاستخدام مش مجانية!
  • Configuration Management — 3 أنشطة: Version management (Git) · System integration · Problem tracking (Jira).
  • Host-Target development: بتطور على الـ Host (IDE + compilers + tools) والبرنامج بيشتغل على الـ Target (libraries + DB). ✏️
  • Open Source: الكود متاح للعموم — بدأت من FSF (Richard Stallman). أمثلة: Linux, Apache, mySQL. نموذج الربح: بيع الدعم والخدمات مش البرنامج (Red Hat).
رخص المصادر المفتوحة الثلاثة: GPL = تبادلية (لو استخدمته لازم تفتح كودك) · LGPL = أخف (للمكتبات، مش لازم تفتح مكوناتك) · BSD = غير تبادلية (حر — ممكن تخليه مغلق ومدفوع). GPL الأكثر تقييداً، BSD الأكثر حرية.
