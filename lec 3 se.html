اكتشف نموذج المخاطر
Barry Boehm · 1988

الدكتور Barry Boehm كان بيشتغل مع مشاريع ضخمة جداً — الدفاع، الفضاء، البنوك. اكتشف إن المشكلة الرئيسية مش في التنفيذ... المشكلة في المخاطر (Risks). فاخترع نموذج الـ Spiral.

🌀
الفكرة: بدل ما تشتغل بخط مستقيم — اشتغل في حلقات (loops). كل حلقة = مرحلة كاملة. وفي كل حلقة، أول حاجة تعملها: حلل المخاطر.
🌀 الـ 4 خطوات في كل Loop

كل دورة في الـ Spiral بتمر بـ 4 مراحل:

  • 🗺️ Planning: نخطط — إيه اللي عايزين نعمله في الدورة دي؟
  • ⚠️ Risk Analysis: نحلل المخاطر — إيه اللي ممكن يغلط؟
  • 🔨 Engineering: نطوّر — بناء prototypes وتجارب لتقليل المخاطر
  • 📊 Evaluation: العميل يقيّم — feedback للدورة الجاية
⚠️ أخطر فخ في الـ Sheet 3 كله!

السؤال: "Which phase involves developing prototypes to mitigate risks?"

كثير بيقولوا "Risk Analysis" — ده غلط!

الإجابة الصح هي Engineering — لأن Risk Analysis بس بتحلل، أما Engineering هي اللي فيها الـ prototypes الفعلية!

الحلقات من الداخل للخارج

كل ما الحلقة بتكبر، المشروع بيكبر: الحلقة الداخلية = Feasibility (هل المشروع ممكن؟) الحلقة الثانية = Requirements (إيه المتطلبات؟) الحلقة الثالثة = Design (إيه التصميم؟) وهكذا لحد ما يتسلم المنتج النهائي.

اكتشف النموذجين الأخيرين
نموذج الـ Prototype

لما العميل مش عارف بالظبط إيه اللي عايزه — بتعمله نموذج أولي (prototype). تخيل إنك بتعمل تطبيق سوشيال ميديا — بدل ما تبني التطبيق كامل، بتعمل version مبسطة جداً، بتعرضها على المستخدمين، وبتاخد feedback. لو مش عاجبهم حاجة — بتغير الـ prototype مش التطبيق كامله!

📐 Prototype Model
  • ✅ يقلل التكلفة الكلية — بتكتشف المشاكل بدري
  • ✅ Risk factor منخفض — التجريب قبل البناء الكامل
  • ✅ يوفر وقت وجهد
  • ❌ التنازل في المتطلبات ممكن يودي لنظام لا يلبي الاحتياجات
  • ❌ Components قديمة ممكن تبقى غير متوافقة مع النظام الجديد
نموذج الـ Rational Unified Process (RUP)

الـ RUP نموذج حديث ومتطور — مشتق من الـ UML. بيمر بـ 4 مراحل رئيسية:

1️⃣
Inception — البداية: إيه الجدوى التجارية للنظام؟ مين المستخدمين؟ نحدد كل الكيانات الخارجية.
2️⃣
Elaboration — التفصيل: فهم المشكلة، تحديد الـ architecture، خطة المشروع، والمخاطر الرئيسية.
3️⃣
Construction — البناء: التصميم، البرمجة، والاختبار — system design, programming, and testing.
4️⃣
Transition — الانتقال: نقل النظام من فريق التطوير للمستخدمين وتشغيله في البيئة الحقيقية.
RUP = Inception → Elaboration → Construction → Transition

اكتشف التفاصيل
📌 Plan-driven vs Agile Processes

نوعان من العمليات:

📋 Plan-driven

كل الأنشطة مخططة مسبقاً والتقدم بيتقاس بناءً على الخطة. مثال: Waterfall.

⚡ Agile

التخطيط تدريجي ويعكس متطلبات العميل المتغيرة. في التطبيق الفعلي، معظم العمليات تأخذ عناصر من الاثنين.

🗂️ الـ 3 Generic Software Process Models

النماذج العامة الثلاثة للبرمجيات

  • 1. The Waterfall Model — مراحل منفصلة ومتميزة من الـ specification والـ development. Plan-driven.
  • 2. Evolutionary Development — الـ specification والتطوير والتحقق متشابكين مع بعض. ممكن plan-driven أو agile.
  • 3. Integration and Configuration (Reuse-oriented) — النظام بيتجمّع من components موجودة قابلة للتهيئة. ممكن plan-driven أو agile.

في التطبيق الفعلي، معظم الأنظمة الكبيرة بتستخدم مزيجاً من النماذج الثلاثة دي.

💡

3 نماذج عامة: Waterfall · Evolutionary · Reuse-oriented

الـ 3 دول ممكن يكونوا plan-driven أو agile — ما فيش "خطأ وصح"، كل مشروع بيختار الأنسب

اكتشف النموذجين
Evolutionary Development — التطوير التطوري

بدل ما تحدد كل المتطلبات في الأول — تبدأ بـ outline وتطور النظام تدريجياً مع العميل. الـ specification والتطوير والـ validation بيحصلوا في نفس الوقت تقريباً.

🧬 نوعان من الـ Evolutionary Development

🔍 Exploratory Development

العمل مع العميل لتطوير النظام النهائي من متطلبات مفهومة جيداً في البداية. يبدأ بالـ well-understood requirements.

🗑️ Prototyping (Throw-away)

هدفه فهم المتطلبات الغامضة. يبدأ بالـ poorly-understood requirements. الـ prototype بيُرمى في الآخر!

✅❌ مزايا وعيوب الـ Evolutionary Model

✅ مزايا

  • يسمح بالتطوير والتحسين التدريجي
  • تسليم مبكر للـ working software
  • feedback مستمر من أصحاب المصلحة
  • يقلل مخاطر فشل المشروع

❌ عيوب

  • يحتاج وقت وجهد أكثر لإدارة التغييرات
  • يحتاج تعاون عالٍ بين أعضاء الفريق
  • مش مناسب للمشاريع ذات المواعيد الثابتة
  • نتائج أقل قابلية للتنبؤ

اكتشف الـ 4 أنشطة
⚙️ الـ 4 Process Activities الأساسية

أي software process بيمر بـ 4 أنشطة رئيسية:

1️⃣
Software Specification (Requirements Engineering)
تحديد الخدمات المطلوبة من النظام والقيود على تشغيله وتطويره.
العملية: Feasibility Study → Requirements Elicitation & Analysis → Requirements Specification → Requirements Validation
2️⃣
Software Design and Implementation
تحويل الـ specification إلى نظام قابل للتنفيذ.
Software design = تصميم هيكل يحقق الـ specification.
Implementation = ترجمة الهيكل لبرنامج قابل للتنفيذ.
3️⃣
Software Validation (Testing)
إظهار أن النظام مطابق لـ specification ويلبي متطلبات العميل.
يشمل: checking, review processes, و system testing.
4️⃣
Software Evolution
البرمجيات مرنة وتتغير. التطوير والصيانة باتوا continuum واحد مش عمليتين منفصلتين.
العملية: Define requirements → Assess existing systems → Propose changes → Modify systems.
📐 Software Design Process — الأنشطة والمخرجات

Design Activities (الأنشطة):

  • Architectural Design — تحديد البنية الكلية للنظام
  • Interface Design — تصميم واجهات المكونات
  • Component Design — تصميم المكونات الفردية
  • Database Design — تصميم قاعدة البيانات

Design Methods (الأساليب):

  • Data-flow model
  • Entity-relation-attribute model
  • Structural model
  • Object models
🔬 Requirements Engineering — الـ 4 أنشطة
  • Feasibility Study — هل النظام ممكن ومجدي؟ يكون رخيص ومحدود المدة.
  • Requirements Elicitation and Analysis — تحديد المتطلبات بمراقبة الأنظمة الحالية، مناقشة أصحاب المصلحة، تحليل النماذج والـ prototypes.
  • Requirements Specification — توثيق المتطلبات. نوعان: User requirements وSystem requirements.
  • Requirements Validation — التحقق من واقعية ودقة واكتمال المتطلبات.
⚙️

4 أنشطة: Specification → Design & Implementation → Validation → Evolution

السؤال التاسع

اكتشف التفاصيل
Incremental Development — التسليم على دفعات

بدل ما تسلّم البرنامج كله دفعة واحدة — تقسّمه لـ increments وتسلّم كل واحد لما يخلص. المتطلبات ذات الأولوية العالية بتيجي في أول الـ increments.

✅ مزايا الـ Incremental Development
  • تسليم مبكر — العميل بياخد قيمة من البرنامج بدري حتى لو مش اكتمل
  • أول increments كـ prototype — بتساعد في استخلاص متطلبات اللاحقة
  • مخاطر أقل لفشل المشروع كله
  • المتطلبات ذات الأولوية العالية بتتختبر أكثر — بتاخد أكبر قدر من الـ testing
⚠️ مشاكل الـ Incremental Delivery

1. معظم الأنظمة محتاجة وظائف أساسية بيستخدمها كل الـ increments — صعب تحدد مين يجيب إيه.
2. التطوير التكراري صعب لو المستخدمين عايزين كل الوظائف.
3. العقود الحكومية الكبيرة بتحتاج specification كامل قبل البداية — الـ incremental مش مناسب.

Software Validation — مراحل الـ Testing الخمسة

الـ testing مش خطوة واحدة — ده سلسلة من الـ 5 مراحل، كل واحدة بتتحقق من جانب مختلف:

🧪 الـ 5 Testing Stages — بالترتيب
1
Unit Testing — اختبار الوحدة

Individual components بيتختبروا — كل function أو module لوحده

Full Lecture Cheat Sheet
Every concept from Lecture 3 — condensed, exam-ready, in English.
01 · THE SOFTWARE PROCESS

A software process = a structured set of activities required to develop a software system.
Every process involves: Specification → Design & Implementation → Validation → Evolution

A software process model = an abstract representation of a process from a particular perspective — its goal is to provide a framework for managing and improving software processes.

Primary goal of any software process = ensure high-quality software products.

Effective process characteristics: Flexibility · Predictability · Adaptability — NOT Rigidity.

02 · PLAN-DRIVEN vs AGILE

PLAN-DRIVEN

All activities are planned in advance. Progress measured against the plan. Example: Waterfall.

AGILE

Planning is incremental, reflects changing customer requirements. In practice, most real processes include elements of both.

03 · THE 3 GENERIC SOFTWARE PROCESS MODELS
ModelKey IdeaType
1. Waterfall Separate & distinct phases of specification and development. Each phase depends on the previous. Plan-driven
2. Evolutionary Specification, development, and validation are interleaved. Software evolves from an initial outline. Either
3. Reuse-oriented System assembled from existing configurable components. Requirements modified to fit what's available. Either
04 · WATERFALL MODEL ★★★

Phases in order: Requirements Definition → System & Software Design → Implementation & Unit Testing → Integration & System Testing → Operation & Maintenance.
Key words: "linear", "sequential", "each phase depends on previous".
NOT a phase in Waterfall: Iteration — Waterfall does each phase exactly once, no loops.

Advantages: Longer operational life · Meets requirements · Excellent documentation · Less need for supporting systems.
Disadvantages: Expensive to maintain · Difficult to use · Requires research into user needs · Difficult to customize.

05 · EVOLUTIONARY DEVELOPMENT

Two types:
• Exploratory Development — Work with customers to evolve a final system from well-understood initial requirements.
• Prototyping (throw-away) — Understand system requirements starting from poorly-understood requirements. Prototype is discarded.

Concurrent activities: Outline description → [Specification / Development / Validation happening together] → Initial version → Intermediate versions → Final version.

Advantages: Incremental dev & improvement · Early delivery of working software · Continuous feedback · Reduces project failure risk.
Disadvantages: More time/effort · Requires high collaboration · Not suitable for strict deadlines · Less predictable.

06 · REUSE-ORIENTED DEVELOPMENT

Phases: Requirements Specification → Component Analysis → Requirements Modification → System Design with Reuse → Development & Integration → System Validation.

3 types of reusable components:
1. Web services — developed to service standards, available for remote invocation.
2. Collections of objects — developed as a package to integrate with .NET or J2EE.
3. Stand-alone software systems — configured for use in a particular environment.

07 · THE 4 PROCESS ACTIVITIES
ActivityWhat it does
1. Specification
(Requirements Engineering)		 Define what services are required & the constraints. Process: Feasibility Study → Elicitation & Analysis → Specification → Validation. Two types of requirements: user requirements & system requirements.
2. Design & Implementation Convert specification into an executable system. Software design = design the structure. Implementation = translate into executable program. Design activities: Architectural · Interface · Component · Database design.
3. Validation
(Testing)		 Show system conforms to specification & meets customer requirements. Includes checking, review processes, and system testing.
4. Evolution Software must change over its lifetime in response to customer needs. Development & maintenance are now a continuum, not two separate processes.
08 · PROCESS ITERATION & INCREMENTAL DEVELOPMENT

System requirements ALWAYS evolve — reworking earlier stages is always part of the process for large systems. Two iterative approaches: Incremental development & Spiral development.

Incremental Development: Break delivery into increments. High-priority requirements delivered in early increments.
Advantages: Early value delivery · Early increments act as prototypes · Lower risk of failure · Highest-priority items get most testing.
Problems: Hard to identify common facilities needed by all increments · Users want all functionality · Government contracts need complete specs.

09 · THE 4 EXAM MODELS — SIDE BY SIDE ★★★
ModelMagic KeywordsExam Trap
🌊 Waterfall linear · sequential · phases depend on previous "Iteration" is NOT a phase
⚡ Agile continuous customer involvement · incremental · iterative "Comprehensive documentation" is NOT an Agile principle
🌀 Spiral risk-driven · risk assessment in each phase · loops Prototypes built in Engineering phase, NOT Risk Analysis
V V-Model verification per phase · testing for each dev phase · early defect detection "Linear sequential like Waterfall" is NOT a V-Model characteristic
10 · PROTOTYPE MODEL

Phases: Communication → Quick Design → Modeling Quick Design → Construction of Prototype → Delivery, Deployment & Feedback → (repeat)

Advantages: Stakeholder role is vital (customer response, evaluation, feedback) · Quick response time · Risk can be avoided · Greater customer involvement improves quality.
Disadvantages: Time-consuming (multiple tickets from customer) · Scope difficult to manage if prototype constantly changes · Risk that prototype becomes the final product even if unsatisfactory.

11 · SPIRAL MODEL — 4 SECTORS PER LOOP ★★★
SectorWhat happens
1. Objective SettingSpecific objectives for the phase are defined. Constraints on the process & product identified. Detailed management plan drawn up.
2. Risk Assessment & ReductionRisks identified & evaluated. Risk reduction activities carried out (e.g., prototype if interface risk).
3. Development & Validation (Engineering) ★Prototypes developed to mitigate risks. Development model chosen based on identified risks. This is the phase for building & testing.
4. PlanningProject reviewed. Decision made whether to continue to next loop. Plans for the next phase are drawn up.

Loops from innermost outward: Feasibility → Requirements → Design → Build → … Proposed by Boehm (1988). Each loop = one complete phase.

12 · TESTING STAGES — IN ORDER ★★★
#StageWhat is tested
1Unit TestingIndividual components tested in isolation.
2Module TestingRelated collections of dependent components tested together.
3Sub-system TestingModules integrated into sub-systems. Focus: interface testing.
4System TestingTesting the system as a whole. Focus: emergent properties.
5Acceptance TestingTesting with real customer data to check acceptability for use.

Mnemonic: U → M → Sub → Sys → Accept

13 · RATIONAL UNIFIED PROCESS (RUP)
PhaseGoal
1. InceptionEstablish a business case. Identify all external entities (people and systems).
2. ElaborationUnderstand the problem domain. Establish architectural framework. Develop project plan. Identify key risks.
3. ConstructionSystem design, programming, and testing.
4. TransitionMove system from development community to user community. Make it work in the real environment.

RUP Static Workflows (Figure 2.13):

Business modelling · Requirements · Analysis & design · Implementation · Testing · Deployment · Configuration & change management · Project management · Environment

14 · CASE TOOLS (Computer-Aided Software Engineering)

Software used to support software development and evolution processes. Includes: graphical system model editors, data dictionaries, GUI builders, debuggers, automated translators.

3 CASE Classification perspectives:
• Functional — classified by their specific function
• Process — classified by the process activities they support
• Integration — classified by their organization into integrated units

Key tool types: Planning · Editing · Change management · Configuration management · Prototyping · Method-support · Language-processing · Program analysis · Testing · Debugging · Documentation · Re-engineering.

⚠️ ALL EXAM TRAPS — MEMORIZE THESE

WATERFALL

"Which is NOT a Waterfall phase?" → Iteration — Waterfall has no loops. Requirements gathered in "Requirements Analysis" not "Design".

AGILE

"NOT an Agile Manifesto principle?" → Comprehensive documentation. "Breaking requirements into smaller tasks?" → Iteration Planning (not plain Planning). "Focus of Planning phase?" → Prioritizing user stories & estimating effort.

SPIRAL

"Which phase develops prototypes to mitigate risks?" → Engineering — NOT Risk Analysis. Risk Analysis only identifies risks; Engineering builds the prototypes.

V-MODEL

"NOT a V-Model characteristic?" → "Linear sequential model similar to Waterfall". Testing purpose in V-Model → verify software meets specified requirements.

EVOLUTIONARY

Exploratory starts from well-understood requirements. Throw-away prototyping starts from poorly-understood requirements.

GENERAL

"NOT a characteristic of an effective process?" → Rigidity. Primary goal of software process → ensure high-quality software, not cost reduction.
