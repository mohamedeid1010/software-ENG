📜 THE DAVIS QUOTE

"Establishing the requirements for a computer-based system is one of the most critical phases of software engineering… The hardest single part of building a software system is deciding precisely what to build."

— Davis (paraphrased from the book)

الـ requirements مش مجرد قايمة أمنيات — هي العقد اللي بيحدد بالضبط ايه اللي المفروض يتبنى. لو الـ requirements غلط، كل حاجة بعديها غلط.

⚡ ABSTRACTION LEVELS

الـ requirements بتتكتب على مستويين مختلفين جداً:

HIGH LEVEL (Abstract)

للـ customer — جملة واحدة بسيطة بتوصف الهدف. مش لازم technical.

LOW LEVEL (Detailed)

للـ developer — تفاصيل دقيقة جداً. كل حاجة technically محددة.

✅ KEY INSIGHT

الـ requirements engineering هو عملية تحويل "عايزين نظام ناجح" → عقد دقيق بيحدد بالضبط ايه معنى "ناجح".

🏥 MHC-PMS EXAMPLE — نظام إدارة المرضى

User Requirement (جملة واحدة):
"A nurse shall be able to search the appointments for all clinics on a particular day."

System Requirements (5 تفاصيل دقيقة):

1.1 — A user shall be able to search the appointments lists for all clinics or for a selected clinic on a specified day.
1.2 — A system shall then display a list of all appointments for that day, with name, address, appointment time, and treatment.
1.3 — Following display, the user shall be able to select any of the listed appointments and cancel the appointment.
1.4 — Users of the search function shall be able to specify that appointments shall be sorted by time, doctor, or treatment.
1.5 — Appropriate warning shall be displayed if a patient appointment is cancelled.

✅ RULE

الـ User Requirements بتقول الـ "WHAT" بشكل عام. الـ System Requirements بتقول الـ "WHAT" بشكل دقيق وقابل للتنفيذ.

🎯 كل الـ Requirements من نفس النوع؟

لأ — فيه 3 أنواع مختلفة جداً. والفرق بينهم ممكن يفرق بين نظام ناجح ونظام فاشل.

🔱 THE 3 TYPES
① FUNCTIONAL

بتوصف الخدمات والوظائف اللي النظام المفروض يعملها. "النظام يعمل ايه؟"

② NON-FUNCTIONAL

قيود على الخدمات أو عملية التطوير. "النظام يعمل إزاي؟" — سرعة، أمان، موثوقية.

③ DOMAIN

قيود جاية من مجال تشغيل النظام. قوانين طبية، مالية، قانونية.

💡 امثلة سريعة
Type Example ملاحظة
Functional System shall generate monthly reports for each clinic. وظيفة محددة
Non-Functional System shall be available 08:30–17:30, Mon–Fri. قيد على التشغيل
Domain System shall implement patient privacy as per HStan-03-2006. قانون خارجي
⚠️ EXAM TRAP

الـ Domain Requirements مش نوع منفصل كلياً — هي في الحقيقة Functional أو Non-functional requirements بس مصدرها من بيئة التشغيل (مجال طبي، مالي، قانوني). السؤال ممكن يطلب منك تحدد النوع وتبرر.

📝 Functional Requirements — "الوعود"

النظام لازم يعمل ايه بالضبط؟ وايه اللي بيحصل لما الـ requirements مش complete ولا consistent؟
Reveal the promises →
📋 WHAT ARE FUNCTIONAL REQUIREMENTS?

الـ Functional Requirements بتوصف:

الخدمات والوظائف

النظام يعمل ايه لما الـ user يعمل action معين.

ردود الفعل

النظام يستجيب إزاي في مواقف معينة — error handling, edge cases.

مستوى التفصيل بيعتمد على نوع الـ software والـ users والنظام:

  • → User requirements = high-level, abstract
  • → System requirements = detailed, precise
🏥 MHC-PMS — FUNCTIONAL EXAMPLES

① A user shall be able to search the appointments lists for all clinics or for a selected clinic on a specified day.
② The system shall generate each day, for each clinic, a list of patients expected to attend appointments that day.
③ Each staff member using the system shall be uniquely identified by their 8-digit employee number.

⚡ THE COMPLETENESS & CONSISTENCY PROBLEM
COMPLETE

لازم تشمل وصف كل الـ facilities المطلوبة — مفيش حاجة تتنسى.

CONSISTENT

مفيش تعارض أو تناقض في أوصاف الـ system facilities.

⚠️ THE PAINFUL TRUTH

في الواقع، من المستحيل إنتاج requirements document كامل ومتسق 100%. دايماً بيكون فيه ثغرات — الهدف تقليلها مش إلغاؤها.

🔍 REQUIREMENTS IMPRECISION — مثال "Search"
👩‍⚕️ NURSE (User Intent)

عايزة أدور على أي appointment في أي clinic في المستشفى كلها.

👨‍💻 DEVELOPER (Interpretation)

هعمل search في الـ clinic اللي بتشتغل فيها الـ nurse بس.

💥 RESULT

كلمة "search" في الـ user requirement كانت غامضة — الـ nurse قصدت كل الـ clinics، الـ developer فهم clinic واحدة. النظام اتبنى غلط لأن الـ requirement كان imprecise.

💀 "The Hidden Killers" — Non-Functional Requirements

النظام بيعمل كل وظايفه تمام — بس بيتسكل 30 ثانية لكل request. هل ده نظام ناجح؟
Reveal the hidden killers →
⚡ ما هي Non-Functional Requirements؟

الـ Non-functional requirements بتحدد خصائص وقيود النظام — مش الوظايف نفسها، لكن إزاي النظام يعمل الوظايف دي:

SYSTEM PROPERTIES

سرعة، موثوقية، أمان، حجم التخزين

CONSTRAINTS

I/O device capability, نوع الـ IDE، لغة البرمجة المستخدمة

PROCESS REQs

تحديد IDE معين، development method محدد

💥 KEY FACT

الـ Non-functional requirements أحياناً أهم من الـ Functional! لو مش متحققة، النظام ممكن يبقى useless حتى لو بيعمل كل الوظايف صح.

📦 THE 3 CLASSIFICATIONS
Classification التعريف مثال
Product Requirements قيود على سلوك المنتج المسلّم — execution speed، reliability النظام يكون متاح Mon–Fri 08:30–17:30، downtime ≤ 5 ثواني
Organisational Requirements نتيجة سياسات وإجراءات المؤسسة — process standards، implementation requirements المستخدمين يتحققوا من هويتهم باستخدام health authority identity card
External Requirements عوامل خارجية — interoperability، legislative requirements النظام يطبق قوانين خصوصية المرضى حسب HStan-03-2006-priv
🏥 MHC-PMS — NON-FUNCTIONAL EXAMPLES
PRODUCT REQUIREMENT

The MHC-PMS shall be available to all clinics during normal working hours (Mon–Fri, 08.30–17.30). Downtime within normal working hours shall not exceed five seconds in any one day.

ORGANIZATIONAL REQUIREMENT

Users of the MHC-PMS system shall authenticate themselves using their health authority identity card.

EXTERNAL REQUIREMENT

The system shall implement patient privacy provisions as set out in HStan-03-2006-priv.

🏗️ HOW NFRs AFFECT THE SYSTEM
ARCHITECTURE LEVEL

الـ NFR ممكن تأثر على الـ overall architecture بدل الـ components الفردية. مثال: لو فيه performance requirement قوي، ممكن تضطر تعيد تصميم كل الـ communication بين الـ components.

CASCADE EFFECT

NFR واحد زي الـ security requirement ممكن يولد عشرات الـ functional requirements جديدة وممكن يقيّد requirements موجودة.

📋 WHAT IS THE SRS?

الـ Software Requirements Document (SRS) هو الـ official statement اللي بيحدد ايه المطلوب من المطورين:

INCLUDES

User requirements + System requirements معاً في وثيقة واحدة

NOT A DESIGN DOC

بتقول WHAT — مش HOW. النظام يعمل ايه، مش إزاي يعمله.

CONTRACT BASIS

ممكن تكون جزء من عقد — لازم تكون complete قدر الإمكان

👥 WHO USES THE SRS?
🏢 System Customers
بيحددوا الـ requirements ويتأكدوا إنها بتلبي احتياجاتهم. بيحددوا التغييرات المطلوبة.
👔 Managers
بستخدموا الوثيقة عشان يخططوا للـ bid وخطة التطوير.
⚙️ System Engineers
بيستخدموها عشان يفهموا النظام المفروض يتطور.
🧪 Test Engineers
بيطوروا tests للـ validation بناءً عليها.
🔧 Maintenance Engineers
بيستخدموها لفهم النظام والعلاقات بين أجزائه.

📊 DOCUMENT VARIABILITY

شكل الوثيقة بيختلف حسب:

SYSTEM TYPE

نظام embedded بيحتاج تفاصيل أكتر من web app بسيط

DEVELOPMENT APPROACH

نظام بيتطور incrementally عادة بيكون فيه less detail في الـ SRS

📌 NOTE

فيه standards زي الـ IEEE standard لكتابة الـ SRS — بس بيتطبق أكتر على large systems engineering projects.

Reveal the 5 ways →
📝 5 WAYS TO WRITE REQUIREMENTS
Notation الوصف متى تستخدمه؟
Natural Language جمل مرقمة بلغة طبيعية — كل جملة requirement واحدة الأكثر استخداماً — للـ user requirements
Structured Natural Language لغة طبيعية على template/form محدد — كل field بيحتوي معلومة معينة لما تريد consistency بدون ambiguity كبير
Design Description Languages بيستخدم لغة زي programming language لتحديد الـ requirements نادر الاستخدام حالياً — مناسب للـ interface specifications
Graphical Notations رسوم بيانية + text annotations — UML use case and sequence diagrams شائع جداً — لتوضيح العلاقات والتفاعلات
Mathematical Specifications notations رياضية مبنية على state machines أو set theory يقلل الـ ambiguity — لكن العملاء مش بيفهموه
⚠️ PROBLEMS WITH NATURAL LANGUAGE
① LACK OF CLARITY

الدقة صعبة بدون ما الوثيقة تبقى صعبة القراءة. تعارض بين precision وreadability.

② REQUIREMENTS CONFUSION

الـ functional والـ non-functional requirements بتتخلط مع بعض في نفس الجملة.

③ REQUIREMENTS AMALGAMATION

عدة requirements مختلفة بتتكتب مع بعض في جملة واحدة — صعب تتعرف عليها منفصلة.

📋 REQUIREMENTS SPECIFICATION — THE BASICS

عملية الـ Requirements Specification هي كتابة الـ user وsystem requirements في وثيقة واحدة:

USER REQUIREMENTS SPEC

لازم يفهمها الـ end-users والـ customers اللي مش عندهم background تقني

SYSTEM REQUIREMENTS SPEC

تفاصيل أكتر — ممكن تشمل معلومات تقنية. قد تكون جزء من عقد.

✅ CRITICAL POINT

الـ requirements ممكن تكون جزء من عقد للـ system development — لذلك من المهم جداً تكون complete قدر الإمكان.

💉 The Insulin Pump — درس حقيقي في الـ Specifications

نظام طبي حقيقي لحساب جرعة الأنسولين. إزاي نكتب الـ requirements بشكل structured وtabular؟
Reveal the insulin pump specs →
📋 FORM-BASED (STRUCTURED) SPECIFICATIONS

الـ Structured Specifications بتستخدم template ثابت بيحتوي على:

COMPONENTS OF FORM-BASED SPEC

• Function / Entity definition
• Description of inputs + their sources
• Description of outputs + destinations
• Info needed for computation
• Description of the action
• Pre-conditions and Post-conditions
• Side effects (if any)

WHY USE IT?

يقلل الـ ambiguity الموجود في الـ natural language — كل field بيتكلم عن جانب واحد محدد من الـ requirement.

💉 INSULIN PUMP — FORM-BASED SPEC
Insulin Pump/Control Software/SRS/3.3.2
Function Compute insulin dose: Safe sugar level.
Description Computes the dose of insulin to be delivered when the current measured sugar level is in the safe zone between 3 and 7 units.
Inputs Current sugar reading (r2); the previous two readings (r0 and r1).
Source Current sugar reading from sensor. Other readings from memory.
Outputs CompDose — the dose in insulin to be delivered.
Destination Main control loop.
Action CompDose is zero if the sugar level is stable or falling or if the level is increasing but the rate of decrease is decreasing.

If the level is increasing and the rate of increase is increasing, then CompDose = round((r2 − r1)/4).
If rounded result = 0 then CompDose = MinimumDose.
Requirements Two previous readings so that the rate of change of sugar level can be computed.
Pre-condition The insulin reservoir contains at least the maximum allowed single dose of insulin.
Post-condition r0 is replaced by r1 then r1 is replaced by r2.
Side effects None.
📊 TABULAR SPECIFICATION

الـ Tabular Specification بتكمّل الـ natural language — مفيدة لما يكون فيه عدة سيناريوهات مختلفة لنفس الوظيفة:

Condition Action
Sugar level falling (r2 < r1) CompDose = 0
Sugar level stable (r2 = r1) CompDose = 0
Sugar level increasing AND rate of increase decreasing
((r2 − r1) < (r1 − r0))		 CompDose = 0
Sugar level increasing AND rate stable or increasing
((r2 − r1) ≥ (r1 − r0))		 CompDose = round((r2 − r1)/4)
If result = 0 → CompDose = MinimumDose
✅ WHY TABULAR?

الـ natural language صعب فيه تحدد كل scenarios بشكل واضح. الـ tabular specification بتحدد كل condition وaction مقابلها بشكل لا لبس فيه — مثالي لأنظمة embedded زي الـ insulin pump.

Exam Cheat Sheet

كل حاجة هتحتاجها في الامتحان في مكان واحد

THE 3 TYPES

  • Functional — what the system does
  • Non-functional — constraints on how it does it
  • Domain — constraints from operation domain

USER vs SYSTEM REQS

  • User Req → abstract, natural language, for customers
  • System Req → detailed, structured, for developers
  • SRS includes BOTH
  • SRS = WHAT, not HOW

NON-FUNCTIONAL TYPES

  • Product — behavior of delivered product (speed, reliability)
  • Organizational — org policies (IDE, process standards)
  • External — interoperability, legislative

NFR METRICS

  • Speed → transactions/sec, response time
  • Size → Mbytes, ROM chips
  • Ease of use → training time, help frames
  • Reliability → mean time to failure, availability
  • Robustness → restart time, data corruption %
  • Portability → % target-dependent statements

SRS STRUCTURE (10 CHAPTERS)

  • Preface → Introduction → Glossary
  • User Requirements Definition
  • System Architecture
  • System Requirements Specification
  • System Models → System Evolution
  • Appendices → Index

5 WAYS TO WRITE REQUIREMENTS

  • Natural language sentences
  • Structured natural language (templates)
  • Design description languages (rare)
  • Graphical notations (UML)
  • Mathematical specifications (formal)

PROBLEMS WITH NATURAL LANGUAGE

  • Lack of clarity — precision vs readability trade-off
  • Requirements confusion — functional + NFR mixed
  • Requirements amalgamation — multiple reqs in one sentence

FORM-BASED SPEC FIELDS

  • Function · Description
  • Inputs (source) · Outputs (destination)
  • Action · Requirements
  • Pre-condition · Post-condition
  • Side effects

SRS USERS & THEIR PURPOSE

  • Customers → specify & verify requirements
  • Managers → plan bids & development
  • System Engineers → understand what to build
  • Test Engineers → develop validation tests
  • Maintenance Engineers → understand system

COMPLETENESS & CONSISTENCY

  • Complete = all required facilities described
  • Consistent = no conflicts or contradictions
  • In practice: IMPOSSIBLE to achieve both 100%
  • Imprecision leads to misunderstanding (search example)

MHC-PMS KEY EXAMPLES

  • Functional: search appointments, generate daily lists, 8-digit employee ID
  • Product NFR: available Mon–Fri 08:30–17:30, downtime ≤ 5s/day
  • Org NFR: authenticate via health authority card
  • External NFR: implement HStan-03-2006-priv

INSULIN PUMP — KEY NUMBERS

  • Safe sugar zone: 3–7 units
  • Inputs: r0 (oldest), r1 (previous), r2 (current)
  • CompDose = round((r2-r1)/4)
  • CompDose = 0 when falling or stable
  • CompDose = MinimumDose if result rounds to 0
