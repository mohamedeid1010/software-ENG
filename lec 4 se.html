💡 المشكلة الحقيقية

Rapid development and delivery is now often the most important requirement for software systems.

سببين:

• الشركات بتشتغل في بيئة سريعة التغيير — practically impossible to produce a set of stable software requirements.

• الـ software لازم يتطور بسرعة to reflect changing business needs.

⚔️ المشكلة مع Plan-Driven

الـ Plan-driven development is essential for some types of system — لكنه does NOT meet these business needs في عالم سريع التغيير.

🚀 الحل: Agile Methods

Agile development methods ظهرت في الـ late 1990s.

هدفها: radically reduce the delivery time for working software systems.

مش بتكتمل المتطلبات الأول وبعدين تبني — الاتنين بيحصلوا مع بعض.

⚠️ فخ الامتحان

الـ Agile ما اتعملش في الـ 1980s ولا 2000s — اتعمل في الـ late 1990s تحديداً.

📋 تعريف Plan-Driven

A plan-driven approach is based around separate development stages with the outputs to be produced at each stage planned in advance.

⚠️ Plan-driven is NOT necessarily Waterfall — plan-driven incremental development is also possible.

الـ Iteration occurs within activities, not between them.

⚡ فريق Agile
مدير Agile: "هنبني feature صغيرة... نوريها للعميل... ياخد feedback... نبني تاني feature."
المطور: "والـ requirements document الكامل؟"
المدير: "الـ outputs from the development process are decided through a process of negotiation during the software development process نفسه!"
⚡ تعريف Agile

Agile development: Specification, design, implementation and testing are inter-leaved.

خصائص Agile:

• Inter-leaved — الـ specification والـ design والـ implementation بيحصلوا مع بعض

• Series of versions/increments — النظام بيتطور على مراحل

• Stakeholders involved — العميل جزء من التطوير

• Frequent delivery — نسخ متكررة للتقييم

• Extensive tool support — automated testing tools

• Minimal documentation — focus on working code

🎯 The Aim of Agile Methods

Agile methods aim to reduce overheads in the software process (e.g., by limiting documentation) and to be able to respond quickly to changing requirements without excessive rework.

الـ Agile methods focus on the code rather than the design, and are based on an iterative approach.

⚠️ فخ الامتحان

في الـ Agile، الـ outputs are decided through negotiation — مش من الأول من خلال requirements document كامل.

الـ Manifesto فلسفة. لكن الـ Agile عنده 5 مبادئ تانكتيكية تحكم كل قرار في الفريق.

تعرف تحكي عن كل واحد منهم في الامتحان؟

اضغط لتكتشف القصة ↓
5 مبادئ من الـ slides مباشرةً
المبدأ التعريف الكامل
1. Customer involvement Customers should be closely involved throughout the development process. Their role is to provide and prioritize new system requirements and to evaluate the iterations of the system.
2. Incremental delivery The software is developed in increments with the customer specifying the requirements to be included in each increment.
3. People not process The skills of the development team should be recognized and exploited. Team members should be left to develop their own ways of working without prescriptive processes.
4. Embrace change Expect the system requirements to change and so design the system to accommodate these changes.
5. Maintain simplicity Focus on simplicity in both the software and the development process. Wherever possible, actively work to eliminate complexity.
🎯 Agile Applicability — امتى تستخدم Agile؟

1. Product development where a software company is developing a small or medium-sized product for sale.

Virtually all software products and apps are now developed using an agile approach.

2. Custom system development within an organization, where there is a clear commitment from the customer to become involved and where there are few external rules and regulations.

⚠️ امتى Agile مش مناسب؟

لو الـ system كبير جداً، أو فيه قوانين صارمة (زي aviation أو medical devices)، أو العميل مش مستعد يشارك بجدية — هنا Agile مش الاختيار الصح.

📖 تعريف XP

Extreme Programming (XP) is a very influential agile method, developed in the late 1990s, that introduced a range of agile development techniques.

XP takes an extreme approach to iterative development.

XP is the most specific of the agile frameworks regarding appropriate engineering practices.

🔗 XP والـ Agile Principles — العلاقة

• Incremental development ← through small, frequent system releases

• Customer involvement ← full-time customer engagement with the team

• People not process ← through pair programming, collective ownership, avoiding long hours

• Change ← supported through regular system releases

• Maintaining simplicity ← through constant refactoring of code

⚠️ ملاحظة مهمة

XP has a technical focus and is NOT easy to integrate with management practice in most organizations. So while agile development uses practices FROM XP, the method as originally defined is not widely used today in its pure form.

الـ XP عنده 10 ممارسات يومية محددة جداً. بتعرف تحكي عن كل واحدة منهم؟

ده أكتر جزء بييجي في الامتحان — محتاج تحفظ كل practice وتعريفها.

اضغط لتكتشف القصة ↓
📋 XP Practices (a) — الخمسة الأولى
الممارسةالتعريف
1. Incremental planning Requirements are recorded on story cards and the stories included in a release are determined by the time available and their relative priority. Developers break stories into development Tasks.
2. Small releases The minimal useful set of functionality that provides business value is developed first. Releases are frequent and incrementally add functionality.
3. Simple design Enough design is carried out to meet the current requirements and no more.
4. Test-first development An automated unit test framework is used to write tests for a new piece of functionality before that functionality itself is implemented.
5. Refactoring All developers are expected to refactor the code continuously as soon as possible code improvements are found. This keeps the code simple and maintainable.
📋 XP Practices (b) — الخمسة التانية
الممارسةالتعريف
6. Pair programming Developers work in pairs, checking each other's work and providing the support to always do a good job.
7. Collective ownership The pairs work on all areas of the system, so no islands of expertise develop and all developers take responsibility for all code. Anyone can change anything.
8. Continuous integration As soon as the work on a task is complete, it is integrated into the whole system. After integration, all the unit tests in the system must pass.
9. Sustainable pace Large amounts of overtime are NOT acceptable as the net effect is often to reduce code quality and medium-term productivity.
10. On-site customer A representative of the end-user should be available full-time for the XP team. The customer is a member of the development team and is responsible for bringing system requirements.

User stories for specification
Refactoring
Test-first development
Pair programming

(a): Incremental planning · Small releases · Simple design · Test-first · Refactoring
(b): Pair programming · Collective ownership · Continuous integration · Sustainable pace · On-site customer

📖 User Stories — التعريف الكامل

في XP، الـ customer or user is part of the XP team and is responsible for making decisions on requirements.

User requirements are expressed as user stories or scenarios — written on cards.

The development team break them down into implementation tasks. These tasks are the basis of schedule and cost estimates.

The customer chooses the stories for inclusion in the next release based on their priorities and the schedule estimates.

📝 مثال حقيقي من الـ Slides: Prescribing Medication
Prescribing medication (User Story)

The record of the patient must be open for input. Click on the medication field and select either 'current medication', 'new medication' or 'formulary'.

→ If 'current medication': check the dose, enter new dose, confirm prescription.
→ If 'new medication': type first letters of drug name, select from list, confirm dose.
→ If 'formulary': search for drug, select, check and confirm dose.

In all cases, the system checks the dose is within the approved range.
📌 Task Cards من نفس الـ Story
Task 1
Change dose of prescribed drug
Task 2
Formulary selection
Task 3
Dose checking (safety precaution)
⚠️ فخ مهم

الـ User Stories مش requirements document — هي scenarios/stories مكتوبة بلغة بسيطة، وبعدين الفريق يكسرها لـ tasks تقنية.

الـ Software Engineering التقليدي بيقول: "صمّم كودك للتغيير من الأول." الـ XP بيقول: "ده غلط كامل!"

فمين الصح؟ وإيه هو الـ Refactoring بالظبط؟

اضغط لتكتشف القصة ↓
مطور تقليدي: "لازم من أول يوم نصمم الـ architecture بطريقة تستوعب كل التغييرات المستقبلية."
مطور XP: "محدش يعرف إيه هي التغييرات المستقبلية! ده مجرد تخمين غالي."
مطور تقليدي: "طيب نعمل إيه؟"
مطور XP: "نكتب أبسط كود يشتغل دلوقتي. وبعدين نـ refactor باستمرار لما نشوف فرص للتحسين."
📖 التعريف الرسمي

Conventional wisdom: design for change — spend time anticipating changes as this reduces costs later.

XP view: This is NOT worthwhile as changes cannot be reliably anticipated.

XP proposes: Constant code improvement (refactoring) to make changes easier when they have to be implemented.

🔧 الـ Refactoring في العمل اليومي

الفريق بيعمل refactoring حتى لو مفيش سبب فوري — بيدوروا على improvements وبيعملوها على طول.

النتيجة:

• Improves the understandability of software → reduces need for documentation

• Changes are easier to make because code is well-structured

⚠️ لكن: بعض التغييرات بتتطلب architecture refactoring وده بيكون أغلى بكتير.

📋 أمثلة على الـ Refactoring

• Re-organization of a class hierarchy to remove duplicate code

• Tidying up and renaming attributes and methods to make them easier to understand

• Replacement of inline code with calls to methods in a program library

⚠️ فخ الامتحان

Refactoring = تحسين الكود بدون تغيير وظيفته. مش إضافة features جديدة — مجرد تحسين structure وقراءة الكود.

اكتب الـ test... قبل ما تكتب أي كود؟ ده منطقي ولا جنان؟

الـ Test-First Development — أغرب وأذكى ممارسة في الـ XP.

اضغط لتكتشف القصة ↓
طالب: "إزاي أكتب test لكود مش موجود؟"
المطور: "الـ test بيحدد إيه المفروض الكود يعمله. لما تكتب الـ test أولاً — بتعرف بالظبط إيه اللي هتبنيه."
طالب: "وبعدين؟"
المطور: "بتكتب أبسط كود ممكن عشان الـ test يعدي. وبعدين تـ refactor. وبعدين تكتب test جديد. وهكذا."
📖 Test-First Development

Testing is central to XP — the program is tested after every change has been made.

XP testing features:

• Test-first development — write tests before code

• Incremental test development from scenarios

• User involvement in test development and validation

• Automated test harnesses — run all component tests each time a new release is built

🔄 Test-Driven Development (TDD)

• Writing tests before code clarifies the requirements to be implemented.

• Tests are written as programs (not data) so they can be executed automatically.

• All previous and new tests run automatically when new functionality is added — checking that new functionality has not introduced errors.

🤖 Test Automation

Test automation means tests are written as executable components before the task is implemented.

Testing components should be:

• Stand-alone

• Simulate the submission of input

• Check that the result meets the output specification

An automated test framework makes it easy to write executable tests and submit them for execution.

🧪 مثال Test Case: Dose Checking
Test 4: Dose checking

Input: dose (mg) + number of doses per day

Tests:
1. Single dose correct, but frequency too high
2. Single dose too high / too low
3. Single dose × frequency too high / too low
4. Single dose × frequency in permitted range

Output: OK or error message (dose outside safe range)
👥 Customer involvement في الـ Testing

The role of the customer is to help develop acceptance tests for the stories to be implemented in the next release.

⚠️ Problem: People adopting the customer role have limited time and may be reluctant to get fully involved in testing.

⚠️ Problems with Test-First Development

1. Programmers prefer programming to testing — may take shortcuts and write incomplete tests.

2. Some tests are difficult to write incrementally — e.g., complex UIs and display logic.

3. It's difficult to judge the completeness of a set of tests — may not provide complete coverage.

📖 تعريف Pair Programming

Pair programming involves programmers working in pairs, developing code together.

الفوائد الأربعة:

1. Develops common ownership of code and spreads knowledge across the team

2. Serves as an informal review process — each line looked at by more than one person

3. Encourages refactoring — whole team can benefit

4. Reduces risk when team members leave — knowledge is shared

🔧 كيف يعمل الـ Pair Programming؟

• Programmers sit together at the same computer.

• Pairs are created dynamically — all team members work with each other during development.

• The sharing of knowledge that happens is very important — it reduces the overall risks when team members leave.

There is some evidence that a pair working together is MORE efficient than 2 programmers working separately.

✅ الفرق بين Pair Programming و Collective Ownership

• Pair Programming = اتنين بيشتغلوا معاً على نفس الكمبيوتر

• Collective Ownership = أي حد في الفريق يقدر يغير أي جزء في الكود — مفيش "مالك" معين لأي file

⚠️ فخ الامتحان

Pair programming is NOT necessarily inefficient — هو مش بالضرورة بطيء أو مهدر. فيه evidence إنه ممكن يكون أكتر كفاءة.

07 · USER STORIES, REFACTORING, TDD, PAIR PROGRAMMING

User Stories

Requirements expressed as stories/scenarios written on cards. Customer decides priorities. Team breaks into implementation tasks → schedule & cost estimates.

Refactoring

Continuous code improvement even without immediate need. Improves understandability, reduces documentation, makes changes easier. Examples: reorganize class hierarchy, rename, replace inline code.

Test-First / TDD

Write test BEFORE code. Tests are executable programs (not data). All previous tests run when new functionality added. Test automation = executable components run automatically.

Pair Programming

Two developers, one computer. Pairs created dynamically. Spreads knowledge, informal review, encourages refactoring. NOT necessarily inefficient — evidence suggests pair > 2 separate developers.
