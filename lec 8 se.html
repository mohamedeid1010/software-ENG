🧠 WHAT IS SYSTEM MODELING?

الـ System Modeling هو عملية تطوير نماذج مجردة (abstract models) للنظام، كل model بيقدم view أو perspective مختلفة.

GRAPHICAL NOTATION

الـ modeling بقى يعتمد على الرسم البياني — وUML أصبح الـ standard لهذا الرسم

HELP ANALYSTS

بتساعد الـ analyst يفهم وظيفة النظام ويتواصل مع العملاء

COMMUNICATE IDEAS

Models هي لغة التواصل بين الـ developers والـ stakeholders

🔷 UML — Unified Modeling Language

الـ UML هو لغة بصرية standardized لـ model وdesign وdocument الأنظمة البرمجية:

WHAT UML SHOWS

System architecture · Functional flow · Object interactions · Database design · Code structure

WHY USE UML?

Visualize before coding · Communicate design · Reduce ambiguity · Support future maintenance documentation

📌 TWO MAIN CATEGORIES

1. Structural Diagrams — بتوصف الـ static structure: Class, Object, Component, Deployment, Package diagrams

2. Behavioral Diagrams — بتوصف الـ dynamic behavior: Use Case, Sequence, Activity, State, Communication diagrams

🗂 EXISTING vs PLANNED SYSTEM MODELS
Model Typeمتى تستخدمه؟الهدف
Existing System أثناء الـ requirements engineering توضيح ما يفعله النظام الحالي — strengths وweaknesses
New System أثناء الـ requirements engineering وDesign شرح المتطلبات المقترحة لباقي الـ stakeholders وتوثيق النظام للـ implementation
📌 MODEL-DRIVEN ENGINEERING

في الـ model-driven engineering، ممكن تولّد implementation كاملة أو جزئية من الـ system model تلقائياً!

🖼 Use of Graphical Models — متى يكون الـ Model صح؟

مش كل model لازم يكون perfect. الـ purpose بيحدد مستوى الدقة المطلوب. 3 استخدامات مختلفة = 3 مستويات دقة مختلفة.
Reveal the 3 uses →
🎯 3 USES OF GRAPHICAL MODELS
① FACILITATE DISCUSSION

لتسهيل النقاش عن نظام موجود أو مقترح — الـ models ممكن تكون incomplete وincorrect — مهمتها فقط دعم النقاش

② DOCUMENT EXISTING SYSTEM

كطريقة توثيق نظام موجود — الـ models لازم تكون accurate لكن مش لازم complete

③ GENERATE IMPLEMENTATION

كوصف تفصيلي للـ system implementation — الـ models لازم تكون correct AND complete لأن هتولّد code منها

✅ KEY TAKEAWAY

نفس الـ model ممكن يكون "ناقص ومقبول" في discussion، و"ناقص وغير مقبول" لو مستخدم لـ code generation. الـ context هو اللي بيحدد المعيار.

🏛 STRUCTURAL MODELS — DEFINITION

الـ Structural Models بتعرض تنظيم النظام من حيث المكونات ("components") وعلاقاتها.

STATIC MODELS

بتعرض structure الـ system design — مثل الـ Class Diagram. الـ "صورة ساكنة" للنظام.

DYNAMIC MODELS

بتعرض تنظيم النظام أثناء التنفيذ — كيف يتغير أثناء الـ runtime.

بتستخدم الـ structural models لما تكون بتناقش وتصمم الـ system architecture.

📦 CLASS DIAGRAMS — BASICS

الـ Class Diagrams تستخدم في تطوير الـ object-oriented system لعرض الـ classes والـ associations بينها:

OBJECT CLASS

تعريف عام لنوع من الـ system objects — مثل Patient، Doctor، Consultation

ASSOCIATION

رابط بين الـ classes يشير لوجود علاقة ما — مثل Patient "has" PatientRecord

📌 EARLY STAGES

في المراحل الأولى من الـ software engineering process، الـ objects بتمثل حاجات في العالم الحقيقي — patient، prescription، doctor، إلخ.

🧬 Generalization — الـ Inheritance في الـ UML

بدل ما تتعلم كل حاجة عن كل كيان، بنجمّع الخصائص المشتركة في class أعلى. ده الـ Generalization — وهو الـ Inheritance في OOP.
Reveal generalization →
🌐 WHAT IS GENERALIZATION?

الـ Generalization أسلوب يومي لإدارة التعقيد — بدل ما تتعلم خصائص كل كيان، بتجمّع الكيانات في general classes وبتتعلم خصائص الـ class. مثلاً: السناجب والفئران هم rodents — فبيرثوا الخصائص المشتركة.

IN MODELING

لو في تغييرات مقترحة، مش محتاج تراجع كل الـ classes — بس الـ class العام اللي بيتأثر

IN OOP

الـ Generalization بيُنفَّذ بـ class inheritance — الـ lower-level classes بترث الـ attributes والـ operations من الـ superclass

📌 HOW IT WORKS

الـ higher-level classes لها attributes وoperations مرتبطة بها. الـ lower-level classes (subclasses) بترث كل ده وبتضيف attributes وoperations خاصة بيها.

🏥 DOCTOR GENERALIZATION HIERARCHY
Doctor (Name, Phone#, Email | register(), de-register())
├─ Hospital doctor (Staff#, Pager#)
│ ├─ Consultant
│ └─ Team doctor
│ ├─ Trainee doctor
│ └─ Qualified doctor
└─ General practitioner (Practice, Address)
✅ INHERITANCE RULE

الـ Hospital doctor بيرث Name + Phone + Email + register() + de-register() من الـ Doctor، وبيضيف ليهم Staff# + Pager# الخاصة بيه.

🧩 AGGREGATION MODELS

الـ Aggregation بيعرض إزاي الـ classes اللي هي collections بتكون مكوّنة من classes تانية. شبيه بـ "part-of relationship" في الـ semantic data models.

EXAMPLE — PATIENT RECORD AGGREGATION

الـ Patient record مكوّن من:

◇ 1 — 1
Patient
◇ 1 — 1..*
Consultation

الـ diamond ◇ في الـ UML يمثل الـ aggregation — الـ empty diamond يعني aggregation، الـ filled يعني composition.

⚡ BEHAVIORAL MODELS

الـ Behavioral Models هي models للسلوك الديناميكي للنظام أثناء التنفيذ — بتعرض ما يحصل أو ما المفروض يحصل لما النظام يستجيب لـ stimulus.

DATA STIMULUS

بيانات تصل وتحتاج معالجة — مثل sensor readings أو form submissions

EVENT STIMULUS

حدث يحصل ويشغّل الـ processing — ممكن يكون معه بيانات أو لأ

📊 DATA-DRIVEN MODELING

الـ Data-driven models بتعرض تسلسل الأحداث في processing الـ input data لتوليد output:

WHAT ARE THEY?

أنظمة business كتير هي data-processing systems مدفوعة بالبيانات

WHAT THEY SHOW

تسلسل الأحداث في معالجة input data وتوليد associated output

WHEN USEFUL

مفيدة جداً أثناء analysis للـ requirements — بتعرض end-to-end processing

Exam Cheat Sheet

كل حاجة هتحتاجها في الامتحان

SYSTEM MODELING — BASICS

  • Process of developing abstract models of a system
  • Each model = different view/perspective
  • Based on UML (Unified Modeling Language)
  • Helps analysts understand functionality + communicate
  • Model-driven: can generate implementation from model

UML — WHY & WHAT

  • Standardized visual language for model, design, document
  • Shows: system architecture, functional flow, object interactions, DB design, code structure
  • Structural diagrams: Class, Object, Component, Deployment, Package
  • Behavioral diagrams: Use Case, Sequence, Activity, State, Communication

4 SYSTEM PERSPECTIVES

  • ① External — context/environment → Context Model
  • ② Interaction — system↔environment, component↔component → Use Case, Sequence
  • ③ Structural — organization → Class Diagram
  • ④ Behavioral — dynamic behavior → State, Activity Diagram

5 UML DIAGRAM TYPES

  • Activity — activities in a process
  • Use Case — interactions between system & environment
  • Sequence — interactions between actors & system/components
  • Class — object classes + associations
  • State — how system reacts to events

USE OF GRAPHICAL MODELS

  • ① Facilitate discussion — incomplete/incorrect OK
  • ② Document existing system — accurate but not complete
  • ③ Generate implementation — must be correct AND complete

CONTEXT MODELS

  • Establish system boundary — inside vs outside
  • Boundary position has profound effect on requirements
  • Defining boundary = political judgment
  • Context model: shows OTHER systems in environment
  • Process model: shows HOW system is used in business processes
  • UML Activity diagrams → define business process models

MENTCARE CONTEXT (6 SYSTEMS)

  • Mentcare (center)
  • Patient record system
  • Admissions system
  • Management reporting system
  • Prescription system
  • HC statistics system + Appointments system

USE CASE MODELING

  • Developed for requirements elicitation → now in UML
  • Each use case = discrete task with external interaction
  • Actors = people OR other systems
  • Represented graphically (overview) or in detailed tabular form
  • Transfer data: Actors = Receptionist + PRS; Stimulus = user command; Response = confirmation PRS updated

SEQUENCE DIAGRAMS

  • Model interactions between actors and objects within a system
  • Shows sequence of interactions during a use case
  • Objects/actors at top with dotted lifeline vertically
  • Interactions = annotated horizontal arrows
  • View Patient Info: ViewInfo → report → authorize → [OK: info | FAIL: error]

CLASS DIAGRAMS

  • Show classes in system + associations between them
  • Object class = general definition of one kind of system object
  • Association = link indicating some relationship
  • Class box = 3 sections: Name | Attributes | Methods
  • MHC-PMS: Patient, Consultation, Medication, Treatment, Condition, Doctor types

GENERALIZATION

  • Everyday technique to manage complexity
  • Group entities into general classes → inherit characteristics
  • In OOP: implemented via class inheritance
  • Higher-level attributes/operations also belong to lower-level
  • Subclasses inherit AND add specific attributes/operations
  • Doctor → Hospital Doctor → Consultant / Team Doctor → Trainee/Qualified

AGGREGATION + BEHAVIORAL

  • Aggregation: shows how classes (collections) are composed of other classes
  • Similar to "part-of" relationship; diamond ◇ symbol
  • PatientRecord = Patient (1-1) + Consultation (1-1..*)
  • Behavioral: dynamic behavior, stimulus = Data or Event
  • Data-driven: sequence of actions for input→output processing
  • Insulin pump: sensor → compute sugar → calculate insulin → control pump
